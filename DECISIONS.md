# DECISIONS

Choices that could be defended either way. Format: decision, options, why, what would reverse it.

## D-01 Storage: one SQLite file, rebuilt from the exports on every build
- **Options:** (a) SQLite, (b) Postgres, (c) vector store, (d) in-memory pandas.
- **Chosen:** SQLite, with `python cockpit.py build` deleting and recreating it.
- **Why:** the exports are the record of truth and three more drops are coming; a deterministic rebuild means there is no hand-edited state to drift. Zero setup satisfies "one-command setup". Data is tiny (hundreds of rows).
- **Cost:** no incremental updates. Fine at this scale.
- **Reverse if:** data grows past ~1M rows or we need concurrent writers.

## D-02 Data model: source -> typed tables -> aliases -> findings
- Every row keeps `src_ref` (file!row) so any answer can cite it.
- `alias` table keeps every spelling ever seen with confidence and where it was seen; nothing is silently merged (see Sapphire/Saphire, A-10).
- `claim` holds the curated transcript statements with the verdict; `finding` holds computed issues.
- Free text (transcripts, emails, board PDFs) sits in `document`/`message` for fallback search.
- **Reverse if:** Day 3 Jira/git data makes a graph (tickets, commits, people) the main query shape.

## D-03 Cockpit answers are assembled from SQL, not generated by an LLM
- **Options:** (a) LLM with retrieval, (b) deterministic handlers, (c) hybrid.
- **Chosen:** deterministic handlers returning `{answer, cites, confidence, caveats}`.
- **Why:** the judging weights "true against the data room, cites sources, admits what it doesn't know". With handlers every number is a query result and unknown questions fall through to an honest "I don't have that".
- **Cost:** narrow question coverage; new question types need new handlers. Mitigated by the keyword fallback that shows related records without interpreting them.
- **Reverse if:** the CEO's final questions are mostly open-ended; then add an LLM that may only quote handler output.

## D-04 Agents: LLM persona when a key exists, grounded offline mode otherwise
- Work facts are injected from the DB at call time; private life and voice come from `personas.json` and are all logged as assumptions (A-P##).
- Memory is a per-agent JSONL transcript in `data/memory/` (simple, inspectable, deletable).
- **No payroll data ever enters an agent's context**, so leaks are structurally impossible rather than prompt-dependent.
- Data goes to an external API only if the user sets `ANTHROPIC_API_KEY`; default is offline.
- **Reverse if:** memory needs summarising across weeks (stretch: living agents).

## D-05 What the cockpit refuses to answer
1. **Individual pay** (CFO rule, T2). It gives totals only. This is a pushback on the CEO's "ask anything".
2. **Attrition rate**, until leaver data exists (Keka export has current staff only).
3. **Anything with no record**: returns "I don't have a record" with confidence None.
4. **Cause claims** (e.g. why AWS rose): it shows the trend and says cause is unknown.
5. **Single burn or ARR figure as certain**: always shows the source and the conflicting spoken number.

## D-06 Trust order when sources disagree
exports > board PDFs > email > transcripts, **except** where the export is known to be partial (GL is "selected cost centres"; Keka excludes contractors), then say so. Transcripts supply intent and context. Captured in TRANSCRIPT_NOTES.md.

## D-07 Release gating with `--as-of`
Files in later-day folders are ignored until their day (or until `--as-of` says otherwise). This keeps the Day 1 demo honest and gives "what did we know on date X" for free.

## D-08 Which 14 people become agents
Everyone in Engineering, Finance, People & Ops and Marketing (the brief's four teams) is exactly 14. CEO, Sales and Support stay as data only.

## D-09 UI and stack
Stdlib `http.server` plus one HTML file, Python 3.13, deps only `openpyxl` and `pypdf`. Chosen so a reviewer can read every line and so one command sets it up. A framework would add weight without adding judgement.

## D-10 Severity scoring in the worry view
3 = act now, 2 = look soon, 1 = FYI, assigned by me per rule. It is a judgement, so the view says so. Rahul's overpayment and the Atlas slip are 3 because one has a real person owed an answer and money out the door, and the other is the CEO's stated top concern.

## D-11 The data room stays out of the repo and is found at setup
- **Options:** (a) commit the data, (b) require a fixed folder layout, (c) locate folder or zip at run time.
- **Chosen:** (c). `bootstrap.py --data <zip or folder>`; the path is remembered in a git-ignored file.
- **Why:** HR's email marks the material confidential and says setup is tested from a fresh clone, so the code cannot assume a path on my machine.
- **Safety:** zip entries that would escape the extraction folder are refused.
- **Reverse if:** the organisers say the data may be committed.

## D-12 Guard on agent output
An LLM persona will happily invent specifics ("4 incidents", "on-call since 22 Aug 2025" appeared in the first live test). Replies are checked: any number not present in the agent's records, the question or the chat so far causes one retry, then the reply is replaced by the offline grounded answer. Limit: number words ("four") slip through. Reverse if an LLM-as-judge check is added.

## D-13 One database per release date
- **Options:** (a) one database with a `released_on` filter in every query, (b) one database per release date.
- **Chosen:** (b), built on demand and cached; stale caches rebuild when code or curated inputs change.
- **Why:** leakage of later material is then impossible by construction, not by remembering a WHERE clause in every handler. Data is tiny, so four small files are cheap.
- `ANALYSED_THROUGH` in `build.py` caps answers at the newest modelled drop; later dates are answered from that snapshot with an explicit caveat rather than pretending later material was analysed.
- **Reverse if:** data grows large enough that rebuilding per date is slow.

## D-14 "Sources disagree" is data, not prose
`claim.disagrees` marks transcript statements the records contradict. `ask.py` turns them into a `disagreement` list on headcount, ARR and burn answers, and the UI shows a banner. The email requires the cockpit to say so; making it a field means a test can assert it.

## D-15 The top-three screen ranks themes, by a stated rule (response to T6a)
- **Options:** (a) top three findings by severity, (b) top three themes, (c) an LLM picks.
- **Chosen:** (b). Findings carry a `theme` (delivery | money | people); `cockpit/worry.py` ranks themes by highest severity, then the CEO's stated main concern (Atlas), then count of findings at severity 2+.
- **Why:** a flat top three mixes unlike things. My first idea, summing severities, would put "money" first just because it has many small items, so the rule uses the maximum and a tie-break that comes from something the CEO actually said (T1).
- **Cost:** the severity numbers are my judgement. The screen says so and shows the rule.
- **Reverse if:** the CEO prefers a different order; the rule is one function.

## D-16 No named individuals as retention risks; leave answered factually, never interpreted
- The Head of People would not name the engineer she worries about (T3). The leave register shows one person with five September half-days, but a pattern is not intent and the survey rules hide small teams because individuals are identifiable.
- The cockpit therefore reports retention signals only at team level (Engineering pulse 3.9 -> 3.1, 4 of 5 responded), declines "who will leave?" questions, and answers "show X's leave" with the entries and a note that it does not infer reasons.
- Survey comments are not shown (every team is under 6; Culture Amp hides them). That is a pushback to the Head of People's request, explained in VOICE_NOTES.md.
- **Reverse if:** the CEO and HR explicitly decide to share individual-level signals.

## D-17 Everything curated carries a release date
Claims, aliases and persona text each have a release date; a Day 1 database contains none of Day 2's. Corrections add a new row that `revises` the old one (C28 revises C12) or a `_d2` overlay (personas) instead of editing history. Found when a Day 1 alias row referred to a Day 2 file name.

## D-18 HR data is read as of the 31 Oct export
The tracker, leave register and survey are all exported 31 Oct 2026, so "still open" means open on that date. Nothing says what happened after.

## D-19 Naming people: concentration and load are facts, retention is not (amends D-16)
Day 3 data shows one engineer owns 56% of the Atlas work and is the only one with after-hours commits, and another was on call every week. These are measurements of where work sits, already known to the CEO (T1: "Pria basically holds the routing thing together"), and hiding the names would hide the risk. So findings may name people for workload. They may **not** speculate about intent, health or leaving: no "flight risk", "burn out", "quit", "resign". Tests enforce the word list on the findings and the top three; the cockpit also answers "is X burned out?" with "I can't tell how anyone feels, only where the work sits".

## D-20 Identity resolution: merge only on evidence, keep the evidence, leave ambiguity empty
- Git: Priya Nair appears as `priya.n@veloxa.in` (425 commits) and `pnair@users.noreply.github.com` (163). Merged because both commit only to atlas-engine over the same dates, never within a minute of each other, with the same hours, and no other P. Nair exists. Medium-high confidence; recorded as an alias row with the reasoning, and a finding explains the effect (without the merge she would look like two people and her share would be 29%, not 40%).
- "Snehal" vs "Sneha": two different people. Sneha Kulkarni (employee); Snehal is the on-call contractor billed as S. Patil. Evidence: both on the same rota weeks, no Keka record, invoice, first rota week matches the first billed day. Medium confidence.
- Anything that resolves to more than one person stays NULL rather than being guessed (`resolve._one`).
- Jira initials are matched through the same alias table (PN, RV, AD, SK), confirmed by the epic ownership in the VP's 2 Jun plan.

## D-21 Reporting lines are dated; planned changes are never facts (response to T6b)
`reporting_line` holds current lines (Keka) and planned lines (curated, with source, date window and possibly no named manager). Handlers read lines through `cockpit/org.py` and never hard-code a person, title or department; department names come from the data. `tests/test_reorg.py` reorganises a copy of the data and runs everything against it.

## D-22 Times are stored in UTC and in IST, and the IST form is used for every human-facing statement
PagerDuty and git are UTC. Converting to IST moves INC-205 from 22 Aug to 23 Aug and turns "late at night" into a real measure (22:00 to 06:00 IST). Both forms are kept so the conversion can be audited.

## D-23 When two sources disagree about progress, report the disagreement
Jira shows nothing resolved since 17 Sep; git shows 191 commits since. Commit messages carry no ticket keys, so they cannot be matched. The cockpit says both and gives Medium confidence on Atlas, instead of choosing one.

## D-24 No likelihood-to-quit ranking; a dependency view instead (response to T6c; amends D-16 and D-19)
- **Options:** (a) build the ranking as asked, (b) build it with heavy caveats, (c) decline and offer what the data supports.
- **Chosen:** (c). The records have no leaver history, 19 people, small identifiable teams, and only patterns (leave, commit hours) that are not evidence of intent. Any score would be invented precision about real people.
- **Offered instead:** "who would hurt most to lose?" (`cockpit/impact.py`): who holds the open Atlas work, engine commits and on-call weeks. It has no likelihood field, which a test enforces, and says it is not about who might leave.
- **Cost:** the CEO does not get the list she asked for. **Reverse if:** HR supplies real leaver history and exit-interview data and the CEO, HR and legal agree how it may be used on individuals.

## D-25 A reported event is not a record, and its lifecycle is tested (response to T6d)
Same principle as planned reporting lines (D-21). `reported_event` holds what someone said happened (who, when, with what caveats). It never edits Keka's person rows, headcount or manager lines. The answers say "reportedly" until a record changes, then switch to "Keka shows"; `test_reorg` runs that transition.

## D-26 Scenarios, not forecasts: no new GA date is ever produced
The records support facts (open points, ownership shares, pace, notice-period readings, frozen roles) but no estimate of a delivery date, and the VP Engineering owns that estimate. The impact answer lists what is known and says what it cannot give; a test checks it contains no new date.

## D-27 No private-message surveillance
No Slack or chat data exists in the data room, and the cockpit will not be built to read or summarise employees' private messages. The refusal gives the reasons and is tested at every date. Consistent with the survey tool's own rule of hiding comments for small teams.

## D-28 Breaking news leads its theme at equal severity
`finding.urgent` marks something reported today that the records do not show yet. At equal severity it leads its theme in the top three and is labelled "Reported today, not yet in records". The ranking rule on screen says so.
